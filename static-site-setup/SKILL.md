# 静的サイト・LP の開発環境構築

## このスキルの中心にある考え方

**推測で設定を書かない。インストールして動かしてから決める。**

環境構築の失敗は、たいてい「ドキュメントを読んで正しそうな設定を書いたが、実際には動かなかった/意図と違う挙動だった」という形で起きる。しかもその発覚は実装が進んだ後になりやすく、そこから直すと手戻りが大きい。

実際にあった例:

- TypeScript の最新版を選んだら、`typescript-eslint` が `<6.1.0` しか対応しておらず、ESLint 構成ごと成立しなかった
- `eslint-config-prettier` を「定番だから」と入れようとしたが、採用した recommended 設定に整形ルールが1つも無く、無効化する対象が存在しなかった
- カスケードレイヤー（`@layer`）でリセットを整理しようとしたが、レイヤーはレイヤー外のスタイルに必ず負けるため、外部CSSを打ち消すという目的に対して逆効果だった
- 汎用リセットを入れようとしたが、既存サイトのCSSが既に同じことをしており、二重適用で詳細度の競合を増やすだけだった

どれもドキュメントを読むだけでは分からず、`npm install --dry-run` を叩く、実際にビルドして出力CSSを見る、といった検証で初めて確定した。**検証は数十秒で終わる。** 推測で進めて後から直すコストと比べれば圧倒的に安い。

だから各項目で「決める前に何を確かめるか」を意識する。判断の根拠になった検証結果は、後で「なぜこうしたか」を思い出せるようドキュメントに残す。

## Astro 案件はテンプレートから始める

単独の静的サイト・LP を Astro で作るなら、このスキルの判断を具体化した `dev-env/astro-template/`（`~/workspace/dev-env/astro-template`）から始める。依存の版・lint 構成・CSS 設計・画像の扱いが検証済みの状態で揃っている。

- 判断の理由と検証結果はテンプレートの `docs/decisions.md` にある。**案件の要件がテンプレートの前提と違う箇所だけ**、このスキルの手順で検討し直す
- 典型的な差分: 既存サイトへの組み込み（`@layer` をやめて `:where(#page-id)` に切り替える）、ファイル名を固定する納品（画像最適化を通さない）、ブラウザサポートの要件
- テンプレートを使って新しい論点が出たら、テンプレートとこのスキルの両方に反映する。依存の版を上げるときは `references/dependencies.md` の手順で検証してから、テンプレートの `docs/decisions.md` も更新する

## 進め方

**項目ごとに区切って、決めては確認を取る。** 一気に全部決めて提示すると、前提がずれていたときの手戻りが大きい。

推奨する順序（前の決定が後の選択肢を狭めるため）:

1. **依存パッケージとバージョン** → `references/dependencies.md`
2. **TypeScript 設定** → `references/typescript.md`
3. **Lint / Format** → `references/lint-format.md`
4. **CSS設計** → `references/css-design.md`
5. **画像・アセット** → `references/assets.md`
6. **Git・エディタ・フック** → `references/git-editor.md`
7. **既存サイトへの組み込み**（該当する場合） → `references/existing-site-integration.md`

各リファレンスには、論点・判断材料・検証コマンド・過去に踏んだ落とし穴が入っている。**その項目に着手する直前に読む。**

順序は絶対ではない。既存サイトへの組み込みが前提の案件なら、7 を先に把握しておくと他の判断（CSSの詳細度設計、納品物の構成）が決めやすくなる。

## 決定を記録する

設定ファイルだけ残しても、半年後に「なぜこの値なのか」が分からなくなる。**判断理由と検証結果をドキュメントに残す。**

特に残す価値があるもの:

- 選ばなかった選択肢と、その理由
- 検証で判明した挙動（出力例つき）
- 「今は保留」にした項目と、確定に必要な情報
- 踏んだ落とし穴と回避方法

置き場所は案件次第だが、`docs/` 配下にトピック別で分け、`AGENTS.md` / `CLAUDE.md` から参照させる形が扱いやすい。エージェントが最初に読むファイルには、**絶対に守る制約**（守らないと納品事故になるもの）を集約しておく。

## このスキルを更新する

環境構築で新しい論点に出くわしたら、**その場でこのスキルに反映する。** 次の案件で同じ検討を一からやり直さずに済む。

更新の判断基準:

- **他の案件でも検討するか** — この案件固有の事情なら、案件のドキュメントに書く
- **推測では分からなかったか** — 検証して初めて分かったことは価値が高い
- **判断を誤りやすいか** — 「定番だから」で選ぶと外すもの、直感と逆の挙動をするもの

反映先:

| 内容 | 書く場所 |
|---|---|
| 既存カテゴリの新しい論点・落とし穴 | 該当する `references/*.md` |
| 新しいカテゴリ | `references/` に新規ファイルを作り、チェックリストと「進め方」に追加 |
| チェックリストの項目漏れ | SKILL.md のチェックリスト |
| 方法論そのものの改善 | SKILL.md の冒頭 |

落とし穴を書くときは、**症状・原因・確かめ方**をセットにする。「こうすべき」だけでは、次に似た状況で応用が効かない。
