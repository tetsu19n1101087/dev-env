# Git・エディタ・運用

## .gitignore

判断が分かれるものは、**理由とセットで決める**。

| 対象 | 典型的な扱い | 判断基準 |
|---|---|---|
| `node_modules/` | 除外 | 議論の余地なし |
| ビルド出力 | 除外 | コマンドで再生成できる |
| フレームワークの生成物（型定義など） | 除外 | 同上 |
| 環境変数ファイル | 除外（`.example` は追跡） | 秘密情報 |
| OS固有ファイル | 除外 | |
| エディタ・ツールの個人設定 | 除外 | チーム共有すべき設定は別ファイルに分ける |
| **開発に必要な外部素材** | **要検討** | 下記参照 |

### 開発に必要な外部素材をどう扱うか

既存サイトの共通パーツ、支給されたアセットなど、**開発に必須だが自前で生成できないもの**は判断が要る。

- **コミットする** — クローンだけで開発を始められる。リポジトリは重くなる
- **除外する** — 軽いが、各自が別途取得する必要があり、取得元をどこかに書き残す必要がある

除外する場合、**再取得の手段がリポジトリ内に残るか**を確認する。参照元も一緒に除外すると、誰も復元できなくなる。

### `.git/info/exclude` の使い分け

`.gitignore` はコミットされ全員に効く。`.git/info/exclude` は**ローカル専用**で共有されない。

「自分の環境にだけ置いてある参考資料」のように、除外の判断を各自に委ねたいものに向く。

```bash
echo "sample/" >> .git/info/exclude
```

### 効いているか確認する

```bash
git check-ignore -v <path>          # どのルールで除外されたか
git status --short --untracked-files=all | wc -l   # 追跡対象の総数
```

## コミット規約

- コミットを意味のある単位に分割する
- メッセージの形式を決める（Conventional Commits など）
- 「コミットして」と言われたときの対象範囲を決めておく（その会話の変更分だけか、未コミット変更すべてか）

機械的な検証（commitlint）を入れるかは規模次第。少人数なら規約の明文化だけで足りることが多い。

### 機械的に検証するなら日本語向けに緩める

規約を決めても強制手段が無いと守られない。commitlint を `commit-msg` フックに入れる。
既定のルールは英語前提なので、日本語で書くなら3つ外す・緩める。

```js
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    // 日本語の件名では大文字小文字と句点のルールが意味を持たない
    'subject-case': [0],
    'subject-full-stop': [0],
    // 日本語は1文字あたりの情報量が多く、既定の72では足りない
    'header-max-length': [2, 'always', 100],
  },
};
```

```sh
# .husky/commit-msg
npx --no -- commitlint --edit "$1"
```

`config-conventional` は**マージコミットを既定で無視する**ので、`Merge branch ...` が弾かれる心配は要らない。

## エディタ設定

### .editorconfig

文字コード・改行コード・インデントを揃える。エディタを問わず効く。

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
indent_style = space
indent_size = 2
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false
```

Markdown だけ行末空白を残す（行末2スペースが改行を意味するため）。

### 推奨拡張機能

`.vscode/extensions.json` にフレームワーク・Lintツールの拡張機能を書いておくと、チームで環境が揃う。`.vscode/settings.json` で保存時フォーマットの挙動も共有できる。

**個人設定と混ぜない。** 共有すべき設定と個人の好みは分ける。

## エージェント向けの指示ファイル

`AGENTS.md`（`CLAUDE.md` はシンボリックリンクにできる）に、**最初に読むべきことだけ**を書く。

```bash
ln -s AGENTS.md CLAUDE.md
```

Git はシンボリックリンクをリンクとして追跡するので、両方コミットできる。

書く内容:

- プロジェクトの概要と関係者
- 詳細ドキュメントへの案内（`docs/` の一覧表）
- **絶対に守る制約** — 守らないと納品事故になるもの
- コマンド一覧
- 現在の状況と未確定事項

**制約は理由とセットで書く。** 「〜してはいけない」だけでは、なぜ駄目なのかが分からず、似た状況で応用が効かない。

詳細は `docs/` 配下にトピック別で分け、`AGENTS.md` からリンクする。1ファイルに全部書くと肥大化して読まれなくなる。

## ブラウザサポートポリシー

**明文化しておくと、実装時の判断が速くなる。** 新しいCSS/JS機能を使うかどうかで毎回迷わずに済む。

検証環境が最新ブラウザのみなら、Baseline Newly Available の機能をフォールバックなしで使える。逆に古い環境を含むなら、その旨を書く。

```
**Browser Support:** 検証環境は各ブラウザ最新版のみ。Baseline Newly Available の機能は
フォールバックなしで使用可。ポリフィルは導入しない。
```

## MCPサーバーの取捨選択

案件に関係ないMCPサーバーが有効だと、ツール一覧がノイズになり、誤って呼ぶ事故も起きる。プロジェクト単位で絞れる。

- グローバル定義のサーバー → `deniedMcpServers` でブロック
- プラグイン経由のサーバー → `enabledPlugins` で `false`

```json
{
  "deniedMcpServers": [{ "serverName": "<name>" }],
  "enabledPlugins": { "<plugin>@<marketplace>": false }
}
```

個人設定ファイル（`.claude/settings.local.json`）に書き、`.gitignore` に入れる。反映は次回セッションから。

**コンテキスト削減が目的なら効果は限定的。** 遅延読み込みされるツールは、名前だけがコンテキストに載っている。会話履歴の方が桁違いに大きい。

## 実装の単位と順序

**セクション単位で、SP → PC の順に実装し、1セクションごとに確認を取る。**

ページ全体をまとめて作らない理由は、デザイン修正が入ったときの手戻りを小さくするため。デザインが並行して動いている案件では特に効く。

```
hero SP → hero PC → 確認 → about SP → about PC → 確認 → ...
```

この順序はCSS設計（モバイルファースト）とも整合する。
