# 既存サイトへの組み込み

既存サイトの一部としてページを作る案件（CMSに納品する、サブディレクトリに配置する）では、**自分のコードだけを見ていると事故る。** 相手側の環境を先に調べる。

## 最初に調べること

支給された既存ファイルや本番ページから、以下を把握する。

### 何が同時に読み込まれるか

```bash
# 共通のインクルードファイルや、本番HTMLのhead部分を読む
cat <shared>/inc/head.html
```

確認する項目:

- **CSS** — ファイル名とサイズ。中身の要素セレクタ（後述）
- **JS** — jQuery などのライブラリ、その他プラグイン
- **計測タグ** — GTM、広告タグ。自分で追加する必要があるか
- **canonical / favicon / robots** — 共通側が持つなら自分で書かない

### 読み込み順

自分のCSSが共通CSSの前か後かで、詳細度の設計が変わる。ビルド出力を見て確認する。

### 既存CSSの要素セレクタ

**クラスセレクタだけでなく、要素セレクタを持っているかが重要。** `h1` `a` `button` `img` などに値が当たっていると、自分のページ内にも影響する。

```bash
grep -oE '^[a-z0-9, ]+\s*\{' <common.css> | head -30
```

見つかったら中身を読み、デザインの妨げになるものを洗い出す。これが reset の方針を決める材料になる（`css-design.md` 参照）。

## サーバー側インクルードへの対応

共通ヘッダー・フッターがサーバー側で差し込まれる場合、**納品HTMLにそのタグを残す**必要がある。

### SSI と PHP の `virtual()` は別物

紛らわしいが、混同すると調査の方向を誤る。

| | SSI | PHP `virtual()` |
|---|---|---|
| 構文 | `<!--#include virtual="/path" -->` | `<?php virtual("/path"); ?>` |
| 処理するもの | Apache の `mod_include` | PHP（`mod_php`）の関数 |
| 見た目 | HTMLコメント | PHPコード |
| 有効化 | `Options +Includes` + `AddOutputFilter INCLUDES` | ファイルがPHPとして処理されること |

`virtual` という語が共通するため「PHPのvirtual()もSSI」と思いがちだが、**PHPの関数**。Apache 専用で、`mod_php` として動作している場合のみ使える。

### `include()` ではなく `virtual()` が使われている理由

置き換えると壊れることがあるので、理由を理解しておく。

| 関数 | 動作 |
|---|---|
| `include()` / `require()` | **ファイルシステム上のパス**を読んでPHPとして評価する |
| `virtual()` | **Apacheのサブリクエストを発行**し、URLとして処理させた結果を取り込む |

`virtual()` はサブリクエストなので、**対象ファイルが他のハンドラで処理される設定なら、その処理を経た結果が返る。**

実際にあった構成: PHPの `virtual()` で読み込んでいる共通ファイルの中に、SSI構文が書かれていた。

```html
<!-- /shared/inc/head.html の中身 -->
<script src="<!--#echo var="site_url" -->/shared/js/app.js"></script>
```

```
1. 親ファイルがPHPとして処理される
2. virtual("/shared/inc/head.html") がサブリクエストを発行
3. head.html が mod_include で処理され <!--#echo --> が展開される
4. 展開後のHTMLが親に埋め込まれる
```

`include()` に置き換えると `<!--#echo -->` が展開されず、ただのコメントとして出力される（`src` が壊れる）。**既存の記述を「同じことだろう」と別の方式に置き換えない。**

### 確認方法

どちらの仕組みが使われているか、共通ファイルの中身から判断する。

```bash
grep -rn '<!--#' <共通ファイルのディレクトリ>/    # SSI構文
grep -rn 'virtual(\|include(\|require(' <ページファイル>  # PHPの関数
```

両方が見つかったら、上記のような組み合わせになっている可能性を疑う。

### テンプレートエンジンとの衝突

フレームワークのテンプレートに `<?php ... ?>` を直接書くと、パーサに解釈されて壊れることがある。生HTMLとして出力する仕組みを使う。

```astro
<Fragment set:html={'<?php virtual("/shared/inc/header.html"); ?>'} />
```

**挿入位置は既存サイトの構造に合わせる。** 典型的には `</head>` 直前、`<body>` 直後、`</body>` 直前の3箇所。

### 開発時に共通パーツが見えない問題

ローカルの開発サーバーではPHPもSSIも動かないため、ヘッダー・フッターが表示されない。レイアウト崩れに気づけない。

環境変数で分岐し、開発時は実ファイルを読み込んで埋め込む:

```astro
---
import fs from 'node:fs/promises';

async function include(path) {
  if (!import.meta.env.DEV) {
    return `<?php virtual("${path}"); ?>`;
  }
  return await fs.readFile(`public${path}`, 'utf-8');
}
---
<Fragment set:html={await include('/shared/inc/header.html')} />
```

共通パーツのCSS・JS・画像も必要になるため、静的配信ディレクトリに一式を置く。

### 整形ツールがタグを壊さないか確認する

ビルド出力を整形する場合、インクルードのタグが保持されるか確かめる。

```bash
grep -c 'virtual(' dist/**/*.html   # 整形前後で数が変わらないか
```

タグを1行に複数並べると、折り返しで分割されることがある（構文上は有効でも見栄えが悪い）。テンプレート側で1行1タグに分けておくと安全。

## 環境ごとの構成を整理する

**開発・テスト・本番で、共通パーツの実体がどこにあるかが違う。** 表にして関係者と認識を合わせる。

| 環境 | 成果物の配置 | 共通パーツ | 確認すること |
|---|---|---|---|
| ローカル開発 | — | リポジトリ内のコピーを読む | レイアウトが崩れないか |
| テストサーバー | 公開パス | ドメインルートに別途配置 | **インクルードが展開されるか** |
| 本番 | 公開パス | 配置しない（既存を使う） | 既存が読み込まれるか |

### テスト環境はファイルを置くだけでは足りない

**インクルードの仕組みによっては、サーバー構成そのものが要件になる。** ファイルを配置しても展開されなければ、本番と違う状態を検証していることになる。

PHPの `virtual()` を使っている場合の要件:

| # | 要件 | 満たさない場合 |
|---|---|---|
| 1 | Apache であること | `virtual()` は Apache 専用 |
| 2 | **`mod_php` であること** | **PHP-FPM では `virtual()` が使えない**（Apacheのサブリクエストにアクセスできない） |
| 3 | 対象拡張子がPHPとして処理される設定 | `<?php ?>` がそのまま出力される |
| 4 | インクルード先がSSI処理の対象（SSI構文を含む場合） | `<!--#echo -->` などが展開されない |
| 5 | SSI変数が定義されていること | **`(none)` に展開される。エラーにならず静かに挙動が変わる** |

**2 は特に見落としやすい。** 現代の一般的な構成（nginx + PHP-FPM、Apache + PHP-FPM）では `virtual()` が動かない。テスト環境を新規に立てるとき、意識せずPHP-FPMを選ぶと本番と挙動が変わる。

**5 のような「静かに壊れる」ものは、生成後のHTMLを直接見て確認する。** 表示が崩れないため、目視では気づけない。

`mod_include` は未定義のSSI変数を**空文字ではなく `(none)` に展開する**（`SSIUndefinedEcho` で変更可能）。

```html
<!-- 定義あり -->
<script src="https://example.com/shared/js/app.js"></script>

<!-- 未定義 -->
<script src="(none)/shared/js/app.js"></script>
```

`(none)/...` は相対パスとして解釈されるため404になる。空文字より発見はしやすいが、**レイアウトは崩れないので目視では気づけない**点は変わらない。

```bash
curl -s <テストURL> | grep -A2 'ebaraclub\|<!--#'
```

サーバー構成の要件は、環境を用意する担当者に先に伝える。

### ローカルで検証環境を作る

開発サーバーでファイルを読み込んで埋め込む方式（前述）では、**インクルードが実際に展開されるかを検証できない**。テスト環境に上げる前に潰すため、本番と同じサーバー構成をローカルに用意する。

PHPの `virtual()` を使っている場合、選択肢はほぼコンテナ一択になる。

| 方法 | `virtual()` | 理由 |
|---|---|---|
| `php -S`（built-in server） | ✗ | **関数が未定義**（`Call to undefined function virtual()`） |
| Laravel Herd / Valet | ✗ | nginx + PHP-FPM |
| **MAMP** | **✗** | **FastCGI 構成で mod_php を積んでいない**（実機で確認した例あり） |
| Homebrew の `httpd` + `php` | ✗ | php formula は CLI と FPM のみ。`--with-apache` は廃止済み |
| **Docker `php:*-apache`** | **○** | **mod_php を同梱** |

`virtual()` は PHP の標準関数ではなく **Apache SAPI にのみ実装されている**（`sapi/apache2handler/php_functions.c`）。実体は `ap_sub_req_lookup_uri()` / `ap_run_sub_req()` という Apache API の呼び出しで、サブリクエストという仕組み自体が Apache 固有のもの。移植のしようがない。

「動くが機能しない」のではなく**関数が存在しない**点に注意する。

```dockerfile
FROM php:8.3-apache
RUN a2enmod include
COPY apache.conf /etc/apache2/conf-enabled/site.conf
```

```apache
<Directory /var/www/html>
  Options +Includes                      # SSI を有効化
  AddType application/x-httpd-php .html  # 拡張子は .html のまま PHP として処理
  AddOutputFilter INCLUDES .html         # PHP の出力に SSI フィルタをかける
</Directory>

SetEnv <SSI変数名> <値>
```

```yaml
services:
  apache:
    build: ./docker
    ports: ['8080:80']
    volumes:
      # 本番と同じ配置にする（成果物は公開パス、共通パーツはドメインルート）
      - ./dist/<公開パス>:/var/www/html/<公開パス>:ro
      - ./public/shared:/var/www/html/shared:ro
```

**ビルド出力をマウントするため、先にビルドが必要。** 無いと空のディレクトリがマウントされて404になる。

#### PHPハンドラと SSI フィルタは共存できる

`.html` を PHP ハンドラに割り当てつつ SSI フィルタもかける構成は、一見矛盾して見えるが動く。ハンドラ（コンテンツ生成）と出力フィルタ（生成後の加工）が別レイヤのため。

```
index.html   → PHP が処理 → virtual("/shared/inc/head.html") 発行
  └ head.html → サブリクエスト。これも .html なので PHP ハンドラを通る
                → PHPコードが無いのでそのまま出力
                → 続いて INCLUDES フィルタが <!--#echo --> を展開
```

実測で確認した挙動。この構成を採る場合は同じ方法で検証しておくとよい。

### 納品物に共通パーツを含めない

**本番には共通パーツを配置しない**（既にサイト側にある）。したがって**納品物に含めてはいけない**。開発用に静的配信ディレクトリへ置いたものがビルド出力にコピーされるため、ビルド後に削除する処理を入れる。

```json
{ "build": "<build> && rm -rf dist/<path>/shared" }
```

この削除処理を消すと納品事故になる。理由をコメントかドキュメントに残す。

## CSSの衝突を防ぐ

自分のCSSが既存サイトの他ページに影響しないよう、**ページ固有のIDやクラスで囲う**。

```scss
:where(#page-id) {
  /* グローバルスタイル */
}
```

`:where()` を使う理由と詳細度の設計は `css-design.md` を参照。

**識別子は数字で始められない。** 公開パスが数字始まり（`1129cp2026` など）の場合、`#1129cp2026` はCSSの構文エラーになる。パスとCSSのIDを別名にする。

```
パス: /campaign/1129cp2026/
ID:   #cp1129
```

## 公開パスの確定を待たない工夫

公開パスは案件の初期に決まらないことが多いが、**`base` / 出力先 / CSSのID / 削除処理のパス**に影響する広範囲な設定になる。

変数として1箇所にまとめておくと、確定後の差し替えが楽になる。

```js
const SLUG = '<スラッグ>';
export default defineConfig({
  base: `/campaign/${SLUG}/`,
  outDir: `./dist/campaign/${SLUG}`,
});
```

確定していない項目は**ドキュメントに「保留」として明記する。** 何が決まれば動けるのかを書いておくと、確認漏れが防げる。

## 納品前の確認

ローカルではPHP/SSIが動かないため、**テスト環境で必ず検証する。**

- インクルードのタグが展開され、ヘッダー・フッターが表示されるか
- 共通CSSと競合してレイアウトが崩れていないか
- ルート相対パスで参照しているアセットが解決するか
- 納品物に共通パーツが混入していないか

## 支給された参考実装の扱い

過去案件の納品物を参考として渡されることがある。**構成をそのまま踏襲することが決まっているわけではない。**

参考実装には欠陥が含まれていることがある。実際にあった例:

- 状態違いのページを複製で作り、原稿修正が片方にしか入らず10箇所差分が発生
- 全画像に `width` / `height` / `loading` / `decoding` が未指定
- モーダルに `aria-*` / フォーカストラップ / Escapeキーが無い
- `console.log` の本番残存、イベントリスナの重複登録
- プリプロセッサ変数のインターポレーション忘れ

**設定やルールをコピーで持ち込まない。** 結果的に同じ値になる場合でも、要件から導き直す。参考実装は「調査対象」として扱い、踏襲しない箇所は理由を記録する。

調査した内容は別ドキュメントにまとめておくと、「なぜこうしなかったか」の根拠として後から参照できる。
